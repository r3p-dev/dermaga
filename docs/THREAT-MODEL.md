# dermaga threat model

This document provides a comprehensive threat model and security analysis for **`dermaga`** (v1.0),
evaluating its security posture, trust boundaries, threat actors, attack vectors, defensive mitigations,
and residual risks in accordance with BRIEF §4, §9, §10 and ARCHITECTURE §1.

---

## 1. System Overview & Scope

`dermaga` is a self-hosted single-tenant Platform-as-a-Service (PaaS) designed for one administrator
on a single hardened Debian 13 VPS. It replaces multi-tenant orchestration platforms (such as Coolify or Dokku)
with an unprivileged, rootless, minimal-attack-surface daemon.

### Architectural Tenets
1. **Unprivileged Execution:** Zero processes run as root after initial installation. The daemon refuses to start under UID 0.
2. **Private Administrative Surface:** The Web UI and API panel bind exclusively to `127.0.0.1:7070` and are reachable only via authenticated SSH local port forwarding.
3. **No Docker / Podman Socket Exposure:** Neither Traefik nor user applications have access to the Podman container engine API socket (`podman.socket` is disabled).
4. **File-Provider-Only Reverse Proxy:** Traefik dynamically loads route configurations generated by Dermaga from strictly validated data structures; it does not query container labels dynamically.
5. **Defense in Depth:** Subordinate UID/GID isolation, Linux capabilities dropped by default (`DropCapability=ALL`), `NoNewPrivileges=true`, cgroups resource limits, loopback host-gateway isolation (`--no-map-gw`), AES-256-GCM secret encryption with column binding, and strict cryptographic audit logs.

## 2. Assets & Trust Boundaries

### 2.1 Security Assets

| Asset | Sensitivity | Storage Location | Protection Mechanisms |
|---|---|---|---|
| **Master Encryption Key** | Critical | `~/.config/dermaga/master.key` | File mode `0600`, created via atomic link, never backed up to restic, excluded from `VACUUM INTO` snapshots. |
| **Admin Credentials** | Critical | SQLite `settings` table | Password hashed via Argon2id ($m=19\text{ MiB}, t=2, p=1$), TOTP secret encrypted via AES-256-GCM (AAD bound to `settings.totp_secret`). |
| **Session Tokens** | High | Browser cookie (`dermaga_session`), SQLite `sessions` | 256-bit cryptographic entropy, stored exclusively as SHA-256 digest in DB, `HttpOnly; SameSite=Strict; Path=/`, 12 h idle / 7 d absolute expiry. |
| **App Secrets & Env Vars** | High | SQLite `env_vars`, plaintext env files `~/.config/dermaga/env/<app>.env` | AES-256-GCM encrypted in DB (AAD bound to column); runtime files mode `0600`; masked in build/deploy logs (minimum 4 characters). |
| **Database Credentials** | High | SQLite `databases` table | AES-256-GCM encrypted (AAD bound); injected at runtime into linked app containers over isolated bridge networks. |
| **Deploy Keys (SSH)** | High | `~/.local/share/dermaga/deploy-keys/<app>` | Ed25519, mode `0600`, dedicated per app, strictly read-only on GitHub. |
| **Webhook Secrets** | High | SQLite `apps` table | AES-256-GCM encrypted (AAD bound); minimum 32 bytes cryptographic randomness. |
| **TLS Certificates & Keys** | High | Named volume `traefik-acme.volume` (`/acme/acme.json`) | Mode `0600`, managed by Traefik, restricted to the Traefik container. |
| **Application Data** | Medium–High | Named volumes `dg-<app>_<vol>` and `dg-db_<name>` | Owned by container UIDs within rootless user namespace; isolated from other apps. |
| **Host System & Kernel** | Critical | Host filesystem, kernel, systemd | Protected by rootless namespaces, nftables firewall, fail2ban, and SSH key authentication. |

### 2.2 Trust Boundaries

```
[ Public Internet ]
       │
═══════╪═══════════════════════════════════════════════════════════════════════════
       │ Boundary 1: Host Perimeter (nftables default-deny: 80, 443, 4222 only)
       ▼
[ Host System / Linux Kernel ]
       │
       ├─ Boundary 2: Rootless User Namespace (UID 1001 / subuids 100000-165535)
       │       │
       │       ├─ Boundary 3: Container Network Isolation
       │       │       ├─ Bridge Network "web": Traefik, App candidate/live containers, dg-hooks
       │       │       └─ Dedicated Bridge Networks "dg-db-<name>": Database + linked App only
       │       │
       │       ├─ Boundary 4: Unix Domain Sockets
       │       │       ├─ CLI Socket: $XDG_RUNTIME_DIR/dermaga/dermaga.sock (0600)
       │       │       └─ Hook Socket: $XDG_RUNTIME_DIR/dermaga/hooks/hooks.sock (0600 in 0700 dir)
       │       │
       │       └─ Boundary 5: Loopback Interface (127.0.0.1)
       │               └─ Panel HTTP Listener: 127.0.0.1:7070 (reachable via SSH tunnel only)
```

1. **Boundary 1 (Host Perimeter):** Enforced by `nftables` default-drop policy and OpenSSH configuration. The only exposed ports are TCP 80, TCP 443, UDP 443 (HTTP/3), and TCP 4222 (custom SSH port).
2. **Boundary 2 (Rootless User Namespace):** All containers and daemon processes run under an unprivileged user (`server`, UID 1001). Container root (`UID 0` in namespace) maps to UID 1001 on the host; non-root container users map into subordinate IDs (`100000+`).
3. **Boundary 3 (Container Network Isolation):** Application containers live on bridge network `web`. Database containers live on dedicated networks (`dg-db-<name>`) inaccessible from `web` or the internet. Pasta runs with `--no-map-gw` to block container access to the host loopback.
4. **Boundary 4 (Unix Domain Sockets):** Filesystem permissions (`0600`) enforce caller identity. The daemon verifies caller UID matching.
5. **Boundary 5 (Loopback Interface):** Panel listens on `127.0.0.1:7070`. Pasta `--no-map-gw` ensures containers cannot route to this port.

## 3. Entry Points & Attack Surface Analysis

### 3.1 Public Edge: Traefik on `:80` and `:443`
- **Exposure:** Public internet.
- **Components:** Systemd socket activation (`traefik-http.socket`, `traefik-https.socket`), Traefik container.
- **Protocols:** HTTP/1.1, HTTP/2, HTTP/3 (QUIC over UDP).
- **Hardening:**
  - Automatic HTTP-to-HTTPS redirect (308 Permanent).
  - Hardened TLS 1.2+ configuration with modern ECDHE/AEAD cipher suites.
  - Strict SNI enforcement (`sniStrict: true`).
  - Request sanitization: `aliasHeadersStrategy: delete`, encoded characters protection (`allowEncodedBackSlash: false`, `allowEncodedNullCharacter: false`).
  - Default response security headers: HSTS (`max-age=31536000; includeSubDomains`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, stripping of `Server` and `X-Powered-By`.
  - Rate limiting (default 100 req/s, burst 50).

### 3.2 GitHub Webhook Endpoint: `/hooks/github/{appId}`
- **Exposure:** Publicly reachable via Traefik router on configured hook hostname (e.g. `https://hooks.r3p.dev/hooks/github/...`).
- **Data Path:** Traefik :443 $\to$ `http://dg-hooks:8080` (dumb TCP forwarder container) $\to$ bind-mounted directory $\to$ `$XDG_RUNTIME_DIR/dermaga/hooks/hooks.sock` $\to$ Dermaga daemon webhook handler.
- **Attacks & Defenses:**
  - *Forged Deliveries:* Evaluates `X-Hub-Signature-256` HMAC-SHA256 using constant-time `hmac.Equal` **before** decoding or JSON parsing.
  - *Payload Flooding:* Enforces 1 MiB body limit via `http.MaxBytesReader`.
  - *Resource Exhaustion:* Per-app rate limiting (token bucket: burst 10, 1 token / 6 s). Unsigned requests do not consume rate limit tokens.
  - *Timing Attacks on App Enumeration:* Unknown `appId` returns `404` after performing dummy HMAC computation to match execution latency of invalid signatures.
  - *Replay Attacks:* Deduplication against SQLite `webhook_deliveries` on `X-GitHub-Delivery`.
  - *Branch / Repo Spoofing:* Matches exact repository fullname and branch; ignores pull requests and unexpected events.

### 3.3 Internal Verification Entrypoint: Traefik `:8081` (`verify`)
- **Exposure:** Internal to container network `web` and rootless network namespace. **Never published to host ports or the internet.**
- **Purpose:** Used during blue-green and recreate deployments by `dermaga probe` to verify that Traefik has hot-reloaded the dynamic configuration.
- **Hardening:**
  - Attached exclusively to temporary `app-<name>-verify` routers carrying an ephemeral cryptographic token (`X-Dermaga-Verify`).
  - Deleted immediately once route verification succeeds.
  - Public routes (`app-<name>`) are never attached to `:8081`.

### 3.4 Admin Panel: `127.0.0.1:7070`
- **Exposure:** Host loopback only (`127.0.0.1`).
- **Access Route:** SSH local port forwarding (`ssh -L 7070:127.0.0.1:7070`).
- **Attacks & Defenses:**
  - *Direct Internet Probing:* Dropped by nftables firewall.
  - *Container Access:* Blocked by pasta's `--no-map-gw` flag; containers cannot resolve or reach host loopback.
  - *DNS Rebinding:* Enforces strict `Host` header check. Requests with `Host` other than `127.0.0.1:<port>` or `localhost:<port>` return HTTP 421 Misdirected Request.
  - *Cross-Site Request Forgery (CSRF):* All mutating requests (`POST`, `PUT`, `DELETE`) require a valid `Origin` header matching the panel listener origin. Missing or foreign `Origin` returns HTTP 403 Forbidden.
  - *Credential Brute Force:* Global exponential login backoff (1s after 5 failures, doubling up to 15m) returning HTTP 429 without invoking Argon2id.
  - *Session Hijacking:* Random 256-bit cookie, stored as SHA-256 digest in DB, `HttpOnly`, `SameSite=Strict`, 12 h idle / 7 d absolute expiration.
  - *Admin Credential Tampering via Web:* Admin password and TOTP management routes (`PUT /api/admin/password`, `PUT /api/admin/totp`, `DELETE /api/admin/totp`) exist **only** on the Unix domain socket (`dermaga.sock`) and are completely omitted from the panel HTTP router (ADR D54).

### 3.5 Host CLI: `dermaga.sock`
- **Exposure:** Local Unix domain socket at `$XDG_RUNTIME_DIR/dermaga/dermaga.sock`.
- **Permissions:** Mode `0600`, parent directory `0700`, owned by user `server`.
- **Security:** Standard POSIX DAC authentication. The kernel guarantees only processes running as UID 1001 (or root) can connect. SSH `AllowStreamLocalForwarding no` prevents remote forwarding of this socket.

## 5. Container Breakout & Isolation Defenses

Dermaga enforces layered isolation for every container:

```
[ Container Process ]
   │
   ├─ User: Unprivileged UID in user namespace (rootless Podman)
   ├─ Capabilities: DropCapability=ALL (minimal whitelist for DB engines)
   ├─ Privileges: NoNewPrivileges=true (prctl PR_SET_NO_NEW_PRIVS)
   ├─ Filesystem: Read-only rootfs (optional), named volumes only, NO host bind mounts
   ├─ Cgroups: Memory cap (--memory), CPU cap (--cpus), PID limit (PidsLimit=256)
   ├─ Storage: Inodes isolated, no docker.sock or podman.socket mount
   └─ Network: Isolated bridge; pasta --no-map-gw prevents reaching host 127.0.0.1
```

### 5.1 Rootless Execution & Subordinate IDs
Containers execute entirely within the rootless user namespace allocated to user `server` (`/etc/subuid` and `/etc/subgid` with 65,536 IDs). An escape from a container lands in the unprivileged `server` user account, not host root.

### 5.2 Linux Capability Whitelisting
All standard application containers drop **all** Linux capabilities:
```ini
[Container]
DropCapability=ALL
NoNewPrivileges=true
```
For managed database engines, empirical testing establishes the strict minimum capability sets required for database daemon initialization (ADR D47):
- **PostgreSQL:** `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID`, `KILL`.
- **MariaDB:** `CHOWN`, `DAC_OVERRIDE`, `SETGID`, `SETUID`, `KILL`.
- **Valkey:** `SETGID`, `SETUID`, `KILL`.

No container runs with `CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, `CAP_SYS_PTRACE`, or `CAP_RAW_IO`.

### 5.3 Sockets and Bind Mounts
- **Zero Engine Socket Sharing:** Unlike typical Docker/Coolify setups, `podman.socket` is **disabled** and never mounted into any container. Traefik operates via file-provider configuration only.
- **No Arbitrary Host Bind Mounts:** User applications may mount only named Podman volumes (`dg-<app>_<vol>.volume`). Host filesystem paths (`/etc`, `/root`, `/home/server`) cannot be mounted by application specifications.

## 6. Credential & Cryptographic Life Cycle

### 6.1 Cryptographic Primitives & Storage
- **Symmetric Encryption:** AES-256-GCM (`crypto/aes` + `crypto/cipher`) using 96-bit random nonces. Ciphertext format: `v1:<hex(nonce)><hex(ciphertext)>`.
- **Column Binding (AAD):** Additional Authenticated Data is set to `table.column` (e.g., `env_vars.value` or `settings.totp_secret`). Ciphertext swapped into another table or column fails decryption.
- **Master Key Security:** 256-bit entropy stored at `~/.config/dermaga/master.key` (mode `0600`). Created using atomic link `link(2)` to prevent overwrite. Refuses to load if permissions allow group or world read. Excluded from automated backups.
- **Password Hashing:** Argon2id with OWASP-aligned parameters ($m=19\text{ MiB}, t=2, p=1$). Memory released explicitly via `debug.FreeOSMemory()` following hash generation to conform to the 30 MB idle memory budget.

### 6.2 Secret Exposure Minimization
- Secrets in database records are decrypted **only** when rendering container runtime `.env` files (mode `0600`).
- API `GET` endpoints return masked or redacted representations. Secrets are revealed only via explicit, audited actions (`dermaga env list --reveal`, `dermaga apps webhook <app>`).
- Build and deployment logs dynamically mask environment variable values ($\ge 4$ characters) before persisting to disk.

## 7. Residual Risks & Mitigations

### 7.1 Residual Risk 1: Shared `web` Network Lateral Movement (Accepted for v1)
- **Description:** All public application containers, the `dg-hooks` relay, and Traefik reside on the single Podman bridge network `web`. A compromised application container can send direct TCP traffic to other containers on `web` (`dg-<other>-<rel8>:<port>`), bypassing Traefik's basic authentication, IP allowlists, security headers, and rate limits. It can also reach `dg-hooks:8080` (protected by HMAC verification in daemon) and Traefik's internal verify entrypoint `:8081` (protected by ephemeral random tokens).
- **Impact:** Lateral probing between co-hosted web applications.
- **Mitigation / Defense:**
  - Database containers are strictly isolated on dedicated networks (`dg-db-<name>`) and **cannot** be reached from `web`.
  - Applications must not trust traffic based on network origin alone.
  - Ephemeral verify tokens protect `:8081` during deploys.
  - *Future Hardening (v2):* Per-app bridge networks (`dg-app-<name>.network`) with Traefik attached to each network, isolating applications entirely from each other.

### 7.2 Residual Risk 2: Host Sudo User Compromise
- **Description:** The user `server` belongs to the `sudo` group. If an attacker achieves full remote code execution under UID 1001 (e.g. by compromising the host SSH private key or exploiting a daemon vulnerability), access to host root depends on `sudo` authentication policy.
- **Impact:** Privilege escalation from `server` to `root`.
- **Mitigation / Recommendation:**
  - Production hosts should configure `SUDO_NOPASSWD=no` in `/etc/sudoers.d/` so that `sudo` requires the user's password.
  - SSH logins must strictly use Ed25519 public key authentication with passphrases. Password login over SSH is disabled.
  - Unattended security updates (`unattended-upgrades`) keep host packages patched.

### 7.3 Residual Risk 3: Build Resource Contention
- **Description:** Building containers directly on the VPS (`podman build`) consumes CPU and RAM. A pathological Containerfile could exhaust build resources.
- **Impact:** Temporary high load during builds.
- **Mitigation:**
  - Strict build cgroup limits: `--memory 2g --memory-swap 2g`, `--cpu-period 100000 --cpu-quota 200000` (max 2 CPUs).
  - Global single-threaded build queue (concurrency 1).
  - 20-minute hard timeout per build.
